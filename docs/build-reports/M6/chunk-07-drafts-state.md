### Decisions
- Finalizing = `confirmDayPlan` unchanged. `saveConfirmedPlan` keeps `planDraftedAt` as history; the saved draft rows are the existing rows, so ids are kept.
- `drafted` (card and cell) = `planDraftedAt` set, `planConfirmedAt` null, and the day is today+1 or later. A draft that arrived as today reads `drafted: false`, `planned: false` (it is just an unplanned today with its rows).
- `discardDraft(db, dayKey, now)` takes a `now` (the contract signature had none) so the rare "also confirmed/closed" case can stamp `updatedAt`. Normal case deletes rows and the days row.
- `saveDraftPlan` throws `ValidationError` if the day is confirmed, closed, or has any session; `saveDayDraft` also throws if nothing is ticked (the UI's `canConfirm` is the gate; use Discard to clear).
- `isDraftable` is the cheap check; `draftableDays` returns the full list (364 days: today+2 .. today+365).
- `usePlanDraft.saveDraft` does not freeze the screen (unlike `confirm`): edits stay visible while the screen navigates back.
- Day number: a lone future draft row cannot lower it (`dayNumber` already clamps a future first row to 1).

### NOTES
1. Migration: `ALTER TABLE days ADD planDraftedAt integer;` (nullable, plain ADD COLUMN). `migrations.js` lists m0000 then m0001 in order. The new snapshot differs from the first only by the id, `prevIds` (points at the first snapshot's id) and the one new column entry. `migrations.test.ts` upgrades a first-migration DB that already has a row and the old row reads `planDraftedAt: null` with its other data intact. Existing installs migrate without loss.
2. Forwarded rows and drafts: `closeByHand` only inserts into `addDays(closedDay, 1)`, so forwarded rows can only land in today+1 (tomorrow), never in a draftable day (>= today+2). The `saveDraftPlan`-on-forwarded-rows case therefore cannot occur. For a drafted tomorrow that then receives forwarded rows: the days row exists, so no createDays; sortOrder continues after the draft rows; a moved task whose taskId is already in the draft is skipped by `takenTaskIds` (unique index safe); `buildPlan` shows draft rows and forwarded rows ticked (forwarded keeps reason 'forwarded'); the unchanged `confirmDayPlan` keeps them. Logic is correct, but no test covers "draft tomorrow + close today with a moved check task". Suggest adding one.
3. `discardDraft` only runs for draftable days via `discardDayDraft`, so it never deletes forwarded or progress rows in practice. The repo-level "also confirmed/closed" branch is defensive and tested.
4. `saveDayDraft` throws `ValidationError('draft', ...)` when nothing is ticked. The Plan screen must disable "Save draft" via `canConfirm` (chunk 8) and offer Discard to clear. Fine as designed.
5. `usePlanDraft.hasDraft` is also true for a drafted tomorrow (mode 'plan'). Harmless; chunk 8 should only show "Discard draft" when `mode === 'draft'`. After `saveDraft` the screen stays `dirty` (edited state is kept, not frozen); documented.
6. Plannable (today if open, tomorrow) and draftable (today+2..today+365) are disjoint and cover today..+365 (today only while open). Tested via edges.
7. A drafted day never visited and now past is auto-closed by rollover with its unticked checks set to let_go, with no marble (draft never counts). Acceptable.
8. `docs/04-domain-rules.md` shows a whole-file diff in `git diff` because the file had mixed CR/CRLF line endings that were normalised; real change is only the 5-line draftable-days paragraph. Minor noise.
9. `rollover()` input changed from `now` to `todayKey` in the working tree and `Day` literals gained `planDraftedAt: null`; callers typecheck and tests pass.
